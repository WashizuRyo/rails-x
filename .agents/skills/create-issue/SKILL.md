# Issueを作成する

目的は、別のエージェントがこのIssueを読んで実装を開始できる状態にすること。
人の判断が必要な仕様・設計・検証方針はIssue作成時に決め、実装開始後はPR作成まで進められるようにする。
このスキルでは実装やPR作成を始めない。

## 手順

1. `AGENTS.md`、関連コード、既存のIssueテンプレートを確認する。
   Gitの接続先とGitHubの情報から対象リポジトリを特定する。
   対象が特定できない場合のみユーザーに確認する。
2. クローズ済みも含めて関連するIssueを検索し、重複を確認する。
   同じ目的のIssueがあればURLと差分を示し、新規作成するか既存を使うか人に判断してもらう。
3. 要望とコードの現状を照らし合わせ、仕様を左右する不明点を整理する。
   コードや既存資料から調べられる事実は自分で調べ、人には仕様の判断を求める。
   質問には推奨回答とその理由を添える。
   今判断できる質問をまとめて聞き、その回答に依存する質問は回答後に行う。
   曖昧な用語や境界条件、要望とコードの現状との矛盾を解消する。
   既存の設計を調べ、変更する責務・データ構造・インターフェース・認証や認可の扱いなど、必要な実装方針を提案する。
   検証方針として、完了条件の各項目に対応するテストの種類・操作や公開インターフェース・参考にする既存テスト・必要な手動確認を提案する。
   挙動や期待結果は完了条件にまとめ、検証方針では対応する項目を参照する。
   選択肢がある判断には採用案と理由を示し、人と合意した実装方針・検証方針をIssueに記録する。
   細かなコードの書き方は実装者に委ね、方針が決まってから日本語でタイトルと本文の案を作る。
   未実装の機能を既存のものとして記載しない。
4. 作成先・タイトル・本文を提示し、人の確認を受けてからIssueを作成する。
   すでにその内容で作成するよう明示されていれば、再確認は不要。
   確認が必要な理由は、このスキルがIssueの内容決定を人に委ねているためと伝える。
5. 確認されたタイトルと本文で、対象リポジトリにIssueを作成する。
   ラベル・担当者・マイルストーンは依頼がある場合のみ指定する。
6. 作成したIssueを取得して内容を確認し、URLを返す。実装開始は人からの別の指示を待つ。

## 本文の構成

`.github/ISSUE_TEMPLATE/task.md` を読み、その見出しに沿って本文を作る。
テンプレートのfrontmatterと説明用コメントはIssue本文に含めない。
